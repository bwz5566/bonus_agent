# 分阶段核算流程设计与现状核查

核查日期：2026-11-16。设计依据的代码基线：main / 129021f。后续分阶段实现已接入智能体主循环，实际入口、暂停确认和实现边界见[运行说明](staged_workflow.md)。本文保留改造前的问题和目标设计，不把尚未实现的逐变量增量缓存等能力视为已交付。

## 结论

保留 bonus_core 的精确数值计算、DSL、来源绑定、独立验算、对账和导出能力，重构 bonus_agent 的任务编排。阶段由程序和验证结果推进，模型在阶段内完成受限的理解和公式构建。计算按依赖图排序，金额校验贯穿流程。计算图、数据关联图、奖金分配层级分别建模，不能把它们当成同一棵树。

业务流程采用“逐对象金额核验 → 总额与范围确认 → 人员分配 → 全量终检 → 导出”。技术上允许提前建立人员、角色和比例等结构，但在总额确认前不发布人员正式金额。按人员汇总后舍入的业务，确认的初始总额应区分未舍入理论总额和最终舍入汇总，不能强行让两者无差异。

## 对 DeepSeek 的核查

截至核查日，官方 API 将 deepseek-flash 对应到 DeepSeek-V4.1-Flash-1017；Flash、deepseek-v4-pro 的上下文均标为 1M，最大输出 384K，支持 JSON 和工具调用。Flash 支持图片，Pro 不支持图片。[官方规格](https://api-docs.deepseek.com/quick_start/pricing/)

官方 /models 提供 context_window（输入与输出合计容量）、max_output_tokens、模态和思考能力。应实际读取并记录服务元数据，第三方或自建服务的能力不能直接沿用官网配置。[模型发现接口](https://api-docs.deepseek.com/api/list-models/)

官方支持关闭思考和 low/high/max 思考强度，默认开启且为 high；思考占输出预算。思考模式下原生工具对话要求回传相应 reasoning_content；当前建议保留 Flash 执行器与 Pro 只读审核器的会话隔离，避免跨模型接管一份工具历史。[思考与工具调用协议](https://api-docs.deepseek.com/guides/thinking_mode/)

官方 1017 模型卡给出了 Agent、推理、代码与视觉评测，但这些没有提供本项目财务规则解释和金额精确率的保证。Flash 关闭思考的实际业务调用也不能直接套用其他推理配置下的榜单结果。最新 Flash 与较早 Pro 的能力关系需按本项目任务评估，不能仅凭名称假定 Pro 对每种任务均更优。[官方模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017)

本地 T13 第2轮日志记录 76 次调用、累计输入 3,676,209 tokens；按步骤记录的76次请求统计，单次最小1,926、中位50,817.5、最大61,296 tokens。因此现有证据不支持“超出1M窗口导致本轮失败”。累计用量不是单次上下文。任务组织、规则适用范围、映射和反馈机制是已证实的故障点；无法据此单独量化模型理解能力的贡献。

## 目标流程及通过条件

| 阶段 | 工作 | 结构化产物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| S0 接收与盘点 | 识别文件用途、核算期间、核算对象、输入/参考答案隔离、所需输出和确认点 | 材料索引、任务合同、解析异常清单 | 每份材料有用途或待核查指针，关键材料可解析；不能按文件名擅自忽略历史数据 |
| S1 规则与证据 | 提取通用口径和各业务分支：适用对象/日期、单位、排除、缺值、舍入、发放、版本优先级 | 带原文位置、适用条件、状态的规则台账 | 关键规则有证据；已知冲突明确阻断受影响节点；不能把本案答复变成跨业务默认规则 |
| S2 数据准备 | 建立实体与有效明细范围，统一完整复合键，定义期间窗口、关系基数、单位及缺值口径 | 标准数据版本、映射、行数去向、身份/关联/期间覆盖报告 | 主键及关联按业务契约有效；未匹配、重复、空值均有可核查结论；不能靠丢行提高匹配率 |
| S3 公式编译 | 把每个公式分解为依赖节点，逐个绑定规则与字段，检查类型、单位、作用域、适用条件和循环依赖 | 有向无环计算图、公式合同、依赖和来源索引 | 必需字段存在，公式可编译、无循环、参数位置与条件正确；禁止先写假设的0/1兜底 |
| S4 基础指标 | 按依赖顺序计算原始明细汇总和基础指标；不依赖未完成的人员分配树 | 基础指标工件、异常和血缘 | 每项指标的数据范围和明细汇总可对账；修改基础输入会使其后继工件失效 |
| S5 逐对象核算与总额 | 计算项目/客户/部门等应得、暂缓、待分配及各奖金类别；独立原文解释并逐对象比对 | 各类逐对象底稿、理论总额、独立差异报告 | 必需对象集合完全一致、逐对象金额和规则一致；不能只验证总额或抽样 |
| S6 总额确认 | 展示总额、对象范围、各类组成、待分配、舍入口径及未决事项，按本流程由用户确认 | 与输入/规则/映射/对象集合/结果语义指纹绑定的确认回执 | 无阻断且回执对应当前版本；仅总额不变不足以保留旧确认 |
| S7 人员分配 | 只使用已确认版本，按角色/比例/资格分配，执行人员汇总舍入、暂缓及已发抵扣 | 人员贡献明细、应得/实发/待分配及舍入差额 | 逐对象去向完整，逐人独立计算一致；舍入差额只能按原文处理，不能随意加给某个人 |
| S8 全量终检与导出 | 核对来源覆盖、对象集合、每人金额、汇总、发放/抵扣、公式与导出文件一致性 | 验证回执、需求格式表格、可追溯核算底稿 | 每个必要验证项均在本版本通过；未通过时仅保留诊断草稿，不发布正式核算结果 |

阶段可以拆成多个受限任务，不必由不同 Agent 执行。无关分支可继续准备，不能让未确认分支的结果进入正式总额。

### 为什么不统一“从最底层向上算”

数据关联图描述明细属于谁；公式图描述指标依赖谁；分配层级描述钱怎么分。项目销售净额通常由明细向上汇总，人员奖金通常从已核定奖金池向下分配，按人汇总后舍入又涉及人员贡献汇总。最终执行顺序由公式依赖决定，不由报表行列或分配层级单独决定。

原文若规定直接逐人核算，计算图也应支持直接产生人员应得，不能强行创造一个先算的独立总池。此时S6可确认适用规则、基础范围与独立核验过的理论汇总，S7处理其后发放步骤；不能为了阶段形状改变业务公式。

### 舍入与确认

确认前可计算人员的未舍入贡献以核实理论总额。人员正式应得按本案原文规定的舍入层级形成。人员舍入后总额与理论总额的差异须明确列示并验证，不能写成任意几分的统一容差。若最终应付总额变化超出确认合同、对象或规则变化，回到确认节点；同一输入与规则版本下不应反复要求确认相同内容。

## 模型分工与上下文合同

| 任务 | 起始路由建议 | 限制 |
| --- | --- | --- |
| 文件分类、表头读取、已验证字段的结构化录入、格式整理 | Flash 关闭思考 | 输出必须符合 schema；不负责金额运算 |
| 单个公式初稿、局部关系推断 | Flash low，遇跨表/作用域/复杂适用条件再按任务路由Pro high | 在封闭的规则和字段集合内工作，输出一个可验证工件 |
| 全局规则适用范围、关键计算图审核 | Pro high | 提供相关原文、字段语义和依赖；不以模型自报置信度代替验证 |
| 独立逐对象/人员金额复核 | 独立Pro high会话 | 从原文重新建式，复用的标准数据必须有单独的数据语义校验；不能让两份公式在同一错误映射上互相证明 |
| 类型、引用、日期、行数、覆盖和精确金额检查 | 程序 | 不消耗模型判断，也不因模型说“正确”而跳过 |
| 孤立格式错误、已识别的缺字段/期间问题 | 确定性反馈 + Flash | 同一问题仅在合法修复后重检；无变化不重试整案 |

这些是初始工程配置，需要用现有案例和合成反例评价，而非宣称其最优。Pro的审核角色本身不证明它比Flash更正确；应记录两者在规则识别、映射、金额核验和成本上的实测表现。若计划改用其他审核模型，先对同一批隔离案例比较。

每次请求仅携带：任务合同摘要、当前节点及依赖、相关规则原文与物理位置、相应表结构和全量统计、待修复反例、预期输出schema。完整原件留在工件存储，程序负责维护规则/来源覆盖索引，模型按需检索；不能因为局部检索而漏掉补充通知或全局约束。

起始预算建议：普通任务8K—24K输入tokens，复杂局部审核尽量控制在64K以内；作为可调的工程软目标，不是官方能力边界或质量保证。为系统指令、工具schema、图片、推理和最终输出共同预留空间。以实际token计量和服务能力控制单次总输入输出，不能只裁剪历史字符数。输出按工件分片；出现length时缩小任务或按受控上限增加预算，不能接受截断公式，也不能直接放开384K输出。

## 闭环、恢复与正确性

每个节点维护 source_refs、rule_refs、input_fingerprint、dependencies、output_ref、validator_receipts、status、attempts。通过回执由程序写入，模型不能调用工具把自身标记为“已通过”。

失败顺序：程序分类 → 定位首个错误节点及反例 → 读取对应原文/原列 → 提出最小修改 → 隔离验证 → 原子应用 → 只重算后继节点 → 重新核验。身份、金额或规则有变化时，受影响确认回执自动失效。错误签名、验证工件和预算跨进程保留；上下文重建不重置次数。没有新输入、有效修改或新证据就不反复执行同一节点。

模型理解不确定但工具执行正常，不等于已验收。可选顾问不可用可以继续准备；必要独立复核不可用则保持等待复核状态。业务口径缺失转为单一、可追踪的问题，程序/协议错误进入修复队列，不把JSON错误包装成财务问题。经验总结只能是带适用条件的检查提示或待审批模板，不得自动推广成新的业务政策。

正确性评价同时覆盖：原文条款/参数、有效数据集合和行去向、规则边界、逐对象金额、逐人员金额、待分配/舍入/暂缓/抵扣、导出文件。独立公式不能查看生产公式答案来迎合；没有参考答案时也要完成这些合同，但不声称能从存在歧义的材料无条件保证唯一正确解释。

## 落地顺序与验收

1. 接入强制阶段状态和验证回执，统一任务计划、依赖和错误归属；优先阻止数据未准备好就启动整案试算。
2. 提供无分配树依赖的原始数据统计和基础指标执行入口；将引擎准备、指标、奖金池与分配阶段解耦，保留原有compute兼容入口及数值语义。
3. 接入逐公式编译/验证、逐对象核算、总额确认与语义失效机制；把现有独立校验前移到对应节点。
4. 将当前manifest扩展为带依赖与证据检索的任务上下文，读取服务能力并实施token预算，按角色路由Flash/Pro和思考强度。
5. 用已隔离的既有案例与合成反例验收：数据顺序改变不影响金额；不参与记录改变不影响相关结果；跨期、重复表头、缺失父实体、分隔符冲突和累计窗口能定位；按人员汇总舍入符合规则；金额不变而对象变化仍使确认失效；重启不会重置错误预算；未通过回执无法导出正式结果。

本设计的核查和后续实现均未启动在线业务模型核算，未修改原案卷、输入或答案。新实现另有分阶段、确认、恢复和金额校验回归；真实业务验收须单独执行。已落地及未落地部分以运行说明为准。
