# 提成核算财务反馈、驳回和版本修订方案

## 现状与目标

固定提成链路已能从材料绑定、项目核算、独立复核、总额确认、人员分配到结果输出。本期已验证完整结果。但 run_chain 的节点回执输入包含材料指纹、节点输入、提示和该节点问题答复，并未将普通对话 message / instruction 纳入回执有效性；普通文字仅在模型实际调用时进入请求。因此，对已通过节点发送“重新计算”并不保证该节点被重新编制。当前确认接口也没有显式的财务驳回或撤销总额确认接口。

目标：保留已核定的工作，财务可以对错误、疑义和新需求发起可追踪修订。程序找出责任节点、重新计算受影响范围并独立复核。旧版本保留审计，不按期望结果凑金额，不因相同总额掩盖项目或人员变化。

## 建议的用户操作

总额确认页展示本版逐项目金额、资金去向和原值/舍入，并提供以下动作：

- **确认本版本总额并继续人员分配**：沿用已有真实确认接口。
- **总额有误，发起复核**：录入已知反例或仅说明怀疑的金额，让程序诊断；真正未知口径及时提问。
- **调整规则或补充材料**：录入正式新要求或更正资料，登记适用范围、原条款、新条款、来源及确认人。

总额已经确认或人员已输出后，仍可对项目金额、人员分配分别提出异议或发起业务变更。项目金额异议使该确认暂不可继续用于人员交付；产生实质变化则再次确认。纯人员分配异议仅在本版项目对象、金额、来源及项目规则合同完全相同的情况下保留原批准。已形成的账册和审批属于历史版本，不删除、不静默改写。

## 修订请求合同

每个财务请求形成版本化结构记录，而不是仅保存在聊天文字中：

```yaml
request_id: 自动生成
case_id: 当前案卷
base_revision: 所异议的核算版本
kind: discrepancy | rule_change | material_correction | recipient_change | report_change
target:
  stage: basis | settlement | output | unknown
  project_keys: []
  indicators: []
  persons: []
description: 用户实际原话
evidence: [] # 文件、表、页、行列、原文及其指纹
observed: null # 当前实际值或具体现象
expected_rule: null # 已确认业务规则，不是强制匹配的答案
effective_scope: this_case | this_period | future_periods | scenario
created_by: 实际用户
created_at: 实际提交时间
status: OPEN
```

异议不授权修改制度；规则变更必须明确被替代条款及范围。参考底稿继续作为独立对账材料，不能作为执行规则或自动选参数的依据。允许财务提出一个项目/指标的反例帮助定位，但不得向模型下达“把数调到与答案相同”的任务。

## 修订工作流

1. **保存反馈和版本**：记录原审批、原合同、原结果和实际问题；当前交付显示正在修订或已被替代，历史版本仍可查。案卷处理中先安全停在可保存的节点，避免多个写入者。
2. **诊断并分类**：区分材料、字段/期间/粒度、业务规则、参数、算法、舍入、名单、报表展示、参考本身错误。仅有总额异议时，先按原始项目键、资金去向及中间指标拆分，结合实际证据和可信度优先检查责任节点。
3. **确定影响范围**：映射到固定 DAG 的责任节点。材料变更按实际依赖源指纹识别失效节点。规则/姓名更改只发到相关节点；不把所有聊天附到全部节点。
4. **产生修复候选**：只重新绑定有问题的合同、原文或名单。保留原候选；新候选先经程序检验，再由独立模型复核。缺口径时提出带来源、例子、影响的实际问题。技术故障和业务冲突分开。
5. **计算并复验**：仅重算受影响节点及下游，同时检查不受影响金额不变；逐项目、角色、人员及边界验证，不只合计。没有实际变化或新证据的重复修复不算进展。
6. **输出新旧差异**：逐项目、指标、参数、人员列出改前改后、差额、来源及归因。若原值本来正确，说明为什么。反馈反例必须有解决证据或合理未采纳理由，不允许只重新发出 PASS。
7. **重新确认与交付**：已批准项目对象、项目金额、口径或相关来源变更时出具新总额供财务真实确认；总额相同但项目分布不同仍须确认。仅人员侧改变且原项目批准范围完全相同的，可以直接继续人员核算。正式文件和回执必须属于同一版本。

## 责任节点与确认范围

| 问题或变更 | 责任节点 | 必须重新完成 | 总额确认 |
|---|---|---|---|
| 客户编码、简称、项目、日期或销售额 | scope_mapping | 项目及相关参考匹配、项目金额、独立复核、下游 | 重新确认 |
| 历史、预算、库存、逾期源数据 | reference_mapping | 受影响系数、项目金额、下游 | 重新确认 |
| 币种、新老定义、区域、阶梯、费率 | project_policy | 受影响规则、项目金额、下游 | 重新确认 |
| 毛利、达成、库存及逾期系数口径 | coefficient_policy | 系数、项目金额、下游 | 重新确认 |
| 冻结、暂扣、项目舍入 | hold_policy | 项目资金去向及下游 | 重新确认 |
| 人名、角色率、个人份额、人员舍入 | roster / settlement | 人员及待分配、角色闭合、最终复核和报表 | 原项目确认范围完全相同时复用 |
| Excel展示或列顺序 | export | 导出和回读、确保金额不变 | 金额及确认范围未变时复用 |

## 实施重点

1. 增加财务反馈持久化记录和网页显式动作。普通解释请求不能创建无意义修订，修改请求不能被已验证回执静默吞掉。
2. 把有效反馈版本与节点归属写入输入指纹；加入依赖失效传播，防止旧候选/旧审批覆盖新要求。已确认口径按适用范围和有效日期管理，不深藏在聊天记录。
3. 增加影响范围和修复前后逐键差异输出；复核用完整责任对象和直接规则证据。
4. 检查候选、计算、独立复核、审批及输出文件属于相同版本，并显示历史/失效状态，避免误认旧文件为最新交付。
5. 保持当前独立节点动态上下文，不再让一个模型自由重写整套公式或按目标金额修改。

## 验收用例

- 相同材料已有 PASS 时，提交客户达成系数异议，须形成可追踪修订并重新核验，不原样复用旧通过状态。
- 一个项目增加一元、另一个减少一元，总额未变，也不得沿用旧项目总额确认。
- 人员份额变化但项目金额未变，验证角色与人员闭合；保留仍准确的项目确认。
- 假设项目提成10000元，库存系数0.9、逾期0.8：加法暂扣3000元，乘法暂扣2800元。只有真实明确的新规则允许改变算法；差异归因须为规则变更。
- 新规则与原制度冲突：明确适用范围、替代条款并解决歧义，不能污染其他月份。
- 财务对已确认项目提出异议：停止旧版人员交付，不改写历史审批；新版本审核及财务确认后继续。
- 反馈缺依据：输出已识别内容、缺项、受影响对象及示例；不猜测和反复问已答事项。
- 用户只问金额怎么算：解释实际规则、公式和原始来源，不触发新修订或重复付费核算。

## 已实施的 P0 / P1 及使用方法

固定链路的财务反馈入口为案卷页面的 **「财务反馈与版本修订」**。本节说明实际工程功能，不改变原本的财务确认责任。

### P0：财务异议、回退、复核和差异

- 「总额有误 / 撤回确认 / 人员金额有误」：填写问题、实际现象、可选的项目四键、原始依据；可以交由程序自动定位，也可以选择已知责任环节。点击「登记并开始复核」或先登记后运行。登记时立刻废止受影响的交付，保留原审批记录、原底稿、旧材料以及历史轮次。
- 不确定责任环节的项目异议进入项目独立复核。已知责任环节则重新绑定该节点的材料/合同，不再因旧 PASS 跳过。节点独立请求只携带分配给自己的反馈、原合同、实际原件及该环节答复；独立复核必须逐条返回已识别内容、核对点、结论和程序能逐字核对的依据。裸 PASS 不算处理了异议。
- 补充、覆盖、删除业务材料沿用原上传入口，同时登记文件变更。只有文件集合、未变更原件指纹、物理 S/T/R 坐标及原合同依赖均可以证明不变时，才复用无关节点；已绑定业务表的单纯数值变化可只重建其责任绑定。新增/删除表、变更制度或不能证明坐标稳定时完整重新绑定。为安全起见，材料清单发生实际变化一律重新确认项目总额。
- 已确认总额的异议提交后同样生效。即使重新计算的合计或全部项目金额相同，新版项目审批凭据也与原审批不同。旧网页提交、旧检查点以及旧结果文件不能覆盖新版审批。核验同一版后重新确认，再继续人员计算。
- 总额待确认时，页面顶部的「总额预核算确认：下一步操作」固定展示正常流程。经办账号也能看到按钮和不可用原因，具备审批权限才可实际确认；程序已更新、当前金额凭据过期时，先显示「重新核验总额（保留已核验节点）」，不允许确认旧预核算。
- 新增 `修订差异.xlsx` 和 `revision_diff.json`：前后总额、逐项目指标及来源、规则合同、材料指纹、人员和角色原值差异、实际反馈及独立复核处理结论。总额待确认时，注明本版人员尚未算；正式输出后才形成完整人员对比。如果原结果无须改变，仍须说明依据并按新审批版本确认。
- 简单说明性查询（例如“某项目怎么算”）可直接在对话框提交。项目或人员的现有核验记录由程序读取并解释，不新建修订、不重新调用模型。明确的新业务规则不会仅凭普通聊天静默成为制度；使用下面的正式变更入口。

### P1：规则版本及人员单独修订

- 「调整业务规则及登记适用版本」：审批人选择要替代的实际已绑定字段、明确新值、理由、来源及适用范围。当前支持的新老分界、汇率调整、累进/全额、负值、达成分子、月均分母、预算重复策略、各缺失系数、暂扣方式、项目/人员精度及人员空比例等，均映射到现有可复用算子。程序只替换正式授权的字段，保留其他原合同，并独立核对；超出既有算子的全新公式仍需要明确制度和扩展算子。
- 默认仅本案生效。另外可明确指定场景的当月、从某月开始或指定有效区间。以受控规则版本记录有效月份、旧值、新值、确认人及来源。相同规则字段若有多个有效版本，后登记的有效版本替代原版本；仅本案的正式修订优先于场景版本。未来生效的版本不改变当前月结果。
- 「仅修订指定项目角色的人员份额」：审批人选择本期完整项目四键和制度角色，录入明确“姓名+百分比”。不得重名或超过100%；未指定余额仍为待分配、不转加别人。项目来源、对象、合同及逐项金额必须完全一致才能保留原总额确认。程序逐角色检查非修改范围原值不变，重新计算人员汇总和核验导出。
- 财务登记、当前状态及正式规则版本分别持久化在案卷 `commission_revisions.json`、`current_commission_version.json` 与场景 `commission_rules/versions.json`。历史快照位于 `out/revisions/<修订版本>/`，原轮次位于 `out/history/第N轮/`。输出底稿增加「版本与审批」表，正式确认校验真实审批、版本及文件指纹。

### 验证范围

使用 `tests/test_commission_revision.py` 验证反馈持久化、版本门禁、相同总额不同项目、适用期间、名单份额、证据校验、依赖范围及网页权限。`tools/verify_commission_revision.py` 可以在独立目录离线复演真实已确认案卷的审批驳回、人员修改、规则修改、材料更新与回读，通过正式 `run_agent` 入口执行真实计算、审批及导出。该脚本使用真实旧合同的受控模型响应替身，**不调用线上模型、不读取参考答案、不替代新的在线自动化验收**。

实际业务复核仍以可引用的制度、材料、财务答复与独立核验为准，最终新需求不能由参考金额直接推导。新版固定报表 `commission-workpaper-v2` 在每项目主底稿中自动展开各角色实际姓名及原值金额，多个收款人自动扩列；额外保留规范化角色明细。区域、实际销售分组、预算、毛利、历史出货月均、库存及逾期等公式引用已核验的项目来源、参考数据明细及历史出货月汇总；汇总人员合计、待分配、尾差和闭合差额均为公式。

已完成案卷可通过「新版报表 / 历史导出修订」→「按当前已核验结果重新导出（不调用大模型）」生成布局的新版本。CLI 对应 `bonus-agent reexport --out 案卷输出目录 --by 实际修订人`。程序先从真实原件逐项目、逐角色和逐人复算，与正式结果完整指纹一致才发布 `out/report_versions/<版本>/result.xlsx` 及 `manifest.json`。不覆盖原结果、不伪造或撤销原财务确认；来源金额发生变化则须走财务修订而非仅改报表。当前页优先展示同一核验轮次的新版报表，旧财务轮次的报表始终标注为历史。
