# 核算验证、证据编译与自动修复

金额由确定性引擎计算；模型负责识别材料和提出规则候选。程序验证失败、执行异常、对象覆盖不完整，均不能标为正式验证通过。不同模型得到相同答案也不能代替原文依据。

## 参数解释与纠错闭环

`Fact.component` 支持 `literal/lower/upper`。`200-750万元` 的共享单位同时作用于两个端点，阶梯 lower 槽自动选择下界；其他槽不猜。`Fact.unit` 支持表头中的明确单位，引用须同时包含单位和裸数。原文与投影保存在台账，冲突检测、编译及最终绑定共用同一数值解释。

绑定当场检查类型、值、目标位置、来源页与上下文，整批失败不留下部分更新。`validate_parameters` 对已经声明目标的区间下界做确定性的局部修复，不改变规则数值或输入。相同绑定和相同版本试算返回 no-op，不把重复执行视为新进展。

循环保护按未解决问题集合计算进展，跨工具和反思上下文保留。连续未消除问题会触发深度思考，持续不变进入有上限的反思/停止，不能因为工具返回成功而无限重置。`review_calculation` 可在证据完整前启动独立全量复核。默认 deepseek-flash 配置使用 pro 执行关键复核及按需思考，日常操作仍使用 flash；本地模型保持本地路由，可显式配置 checker/think_model。

上述 flash 路由的 `checker_required: true` 表示 pro 不可用时明确阻断，不静默退回主模型。上下文超限时最多恢复两次：压缩历史并按需启用强模型，结构化规则、参数台账和未解决问题仍在工作区中；仍超限则保存未完成状态。相同材料、规则、结果与独立算式的全量检查使用缓存，输入版本、结果、算式或执行器变化会失效；缓存不能将执行失败变成通过。

## 身份与金额去向

复合主键在多数组件相同、另一组件冲突时，返回源行、双方编号与 combine 列，不自动按近似名称合并，也不能通过 unmatched: ignore 避开。历史范围外对象不会仅因未匹配而升级为该错误。

`report.distributions` 在奖金池作用域声明 `{name, level, total, pending: [名称], sources}`；`total` 是材料规定的应分配总额。程序逐对象检查总额等于规则分配池加上同层、明确列示的待分配金额，按合计到分比较。名称不能重复使用。已有对账及待分配契约在隔离修复中冻结，不得靠删除或放宽通过。

结构检查识别 `tier_rate(..., ratio(..., zero: ...))` 及变量别名，将最终默认系数与默认达成率混用作为必须修正的问题。显式分母保护或 `tier_ratio` 均可表达正确语义，具体默认值必须来自当批材料。独立复算和按原文记录的行为检查仍负责核对实际业务默认值。

有明确输出要求的场景还必须提供人员独立算式 `people`，并覆盖全部已实名人员及所有待分配项。`mode: allocation` 使用独立权重和独立奖金池复算逐层尾差；`after_sum/per_record` 分别按材料的人员汇总后舍入、逐记录舍入解释。程序逐人对账到分，不能以项目总额相同或个别记录尾差为由跳过。舍入或其他业务口径尚有 `unclear` 时不能正式完成；本案验收答案不用于推导生产默认政策。

实际规则要求按人汇总后舍入时，按人员建立唯一奖金池，参与记录和项目保留为辅助实体。`report.distributions` 的 `rounding: after_sum, level: global` 严格核对舍入前理论总额=人员原值+待分配原值；人员、待分配分别舍入后产生的差额进入独立的“舍入对账”，不擅自分给任何人员。`report.details` 声明辅助对象的独立金额报告，辅助对象底稿与全部报告计算链一并导出。独立算式另给 details 表达式，逐个对象核对；期望表完全没有对应对象也会报缺失，不再忽略整张表。编号仅允许无歧义地省略程序合成的竖线分隔符，禁止按金额选择对应关系。

## 证据参数表

先用 `record_facts` 登记原文参数，再用 `compile_table` 编译，避免把同一比例手工抄入多张表。阈值和比例引用参数名，程序负责百分号与金额单位换算：

```json
{
  "name": "rate",
  "scheme": "monthly",
  "kind": "tier",
  "mode": "excess",
  "rows": [
    {"value": "首档比例"},
    {"lower": "第二档下限", "value": "第二档比例"}
  ]
}
```

只有首档隐含的 0 起点可以省略引用。每个业务阈值、比例、查找值和默认查找值都须有精确位置绑定。公式中的参数可用 `bind_facts` 绑定到 `variables.bonus.expr`。

绑定支持 `方案::/tables/表名/steps/0/1`。JSON Pointer 中 `~` 写成 `~0`，`/` 写成 `~1`，所以业务编号和键中有点号、斜杠也不会被错误拆分。可省略方案限定，但同名位置在多个方案中必须都符合该参数。

多页原文须指定正确页码；`context` 用该页真实的适用标题。表可写 `applies_when` 声明适用条件，调用时条件不成立直接报错。这些条件仍需独立核对其业务含义。

旧案卷缺少来源指纹、单元格绑定时仍可读取、试算，但不能把旧验证直接当作新版本验证。需重新核对原文；必要时用 `remove_facts` 删除旧登记再登记、编译和验算。

## 默认值与期间

`tier_ratio(table, numerator, denominator, default_coefficient, missing: condition)` 将缺失或分母为 0 的默认值直接作为最终系数，不会把它误当比率再查表。默认系数与缺失条件必须由本期材料规定。

`period_value(m01, m02, ..., m12)` 按核算期间结束月选择宽表字段。季度、年度、累计窗口需另按材料明确计算，不能直接把月末取值当成累计预算。

空值、没有匹配行、0、负数和格式错误仍是不同状态；新函数不会替业务决定这些状态该怎么处理。

## 对象范围

实体按有效明细建立时，可在 `define_dataset` 指定 `population_from` 为按实体主键关联的明细表。实体对象集合从过滤后的明细派生，原始输入不会被改写。

同一来源工作表的实体和过滤明细存在多余对象时，程序提示范围不一致。若业务确实要求展示没有有效明细的对象，需要明确依据，而不是把这些对象静默当成正常计算对象。

## 对账与待分配

`report.balances` 声明每个对象上的金额分解：

```yaml
report:
  balances:
    - name: total_decomposition
      level: 项目
      total: gross
      parts: [available, deferred]
      rounding: exact
      sources:
        - doc: 规则说明.md
          quote: "总额等于可分配与暂扣之和"
```

`rounding: exact` 在引擎精度下检查，`cent` 对各项先舍到分再检查；没有可由模型任意放大的容差。对账无对象、表达式错误、金额不闭合或缺来源都会报错。

`report.pending` 支持 `name`、`level`、`expr`、`sources`，在人员汇总中单列待分配金额，`paid` 为 0。它不属于已分到名单的奖金池。按业务定义把人员、待分配和总额接入对账；不要将待分配金额重复计入总包。

程序还检查各级分配、奖金池和已分配人员汇总的守恒关系。待分配行与已经分配的人员行明确区分。

## 独立验证和输出

关联列的单列覆盖相同不能证明完整项目键一致。挂接建议会比较同类候选列的完整组合；同一简称对应多个编码不能直接合并为别名。先落实期间和排除条款，再按全量输入关系核对。待答复的长问题在数字前提、引用字段及关联对象未变且文字高度相似时复用原问题，避免轻微改写重复提问；不据此自动回答或合并不同口径。

提问的 Excel 依据支持 `file/sheet/row/columns`，程序从实际单元格生成引用；同时提供 quote 时仍检查是否相符。带建议的问题若有引用核对失败则退回修正，不能用省略号拼出的数据行支撑建议。不带建议的疑问可保留未通过引用并明确标示。

- 奖金池按声明层级的完整对象集合核对，不按编号中的分隔符数量筛选。
- 独立计算异常、缺方案、缺可发比例、集合不一致或没有定论均为未完成验证。
- 数值反证不会因为重复采样时某次赞同主结果而消失。
- 验算对象覆盖金额极值、零值、实际命中的条件和阶梯档位；关联实体的分支通过追踪依赖关联到分配对象。
- 豁免绑定规则、输入文件、期间和答复版本；相关内容改变后需重新核对。错误页码不能通过重复提交绕过。
- 输入在一轮运行中改变，会阻断继续计算，需重新建立工作区，避免旧原文缓存与新数据混用。

输出新增 `validation.json`，记录输入/规则指纹、检查状态和反例。状态包括 `PASS`、`FAIL`、`ERROR`、`INCOMPLETE`、`NOT_APPLICABLE`。执行检查出错不会被写成通过。

## 自动修复

1. 用 `validation_report`、`explain` 和原文找到第一处分歧。
2. 用 `preview_repair(parts, reason, scheme)` 在副本中试算；原工作区不变。
3. 用 `verify_repair` 完成候选的独立样本验算。
4. 用 `apply_repair` 重新检查来源、独立全量复算、样本、程序检查与金额闭合，全通过才应用。

候选不能修改输入、台账、答案、原有校验、人工调整或冻结的对账契约。每个基础版本最多 6 次候选试算；基础输入或规则改变使候选失效，已应用候选不能再次应用。

场景配置的验收案例作为服务器端冻结回归，在候选应用前重新计算。修复模型只收到案例通过/失败状态，不收到参考答案。没有配置回归时明确记录不适用，不能宣称已经跨案例验证。

应用只更新本地案卷，不等于正式发布。发布规则版本必须有验收用例并通过。经过验证、确认且发布的修复可保存为场景经验，标记“仅原案验证”；它用于建议检查，不成为其他客户或其他期间的默认费率。

## 测试与限制

`tests/test_validation_contracts.py` 使用真实验证门槛，覆盖异常、空比较、错位参数、来源变化、默认值、跨月取值、金额不闭合、数据重排性质、隔离修复和保留答案隔离。其他功能测试用标记隔离不相关的模型响应；独立验证的测试显式提供参考响应，不以生产代码中的测试模式放宽门槛。

自然语言解释和数据映射仍可能存在歧义，独立复算也仍共享部分基础设施。系统不能证明任意新规则的业务含义永远正确；不明确时应给出差异和待确认状态。正式发布的独立验收、边界案例和人工口径确认仍有必要。

## 有界纠错与模型分工

案卷输出目录的 `recovery.json` 保存失败对象、错误摘要、累计次数、已咨询的问题和未解决事项。相同输入、期间、财务答复、对话及代码版本下，反思、自动接续和重启不会清空记录。同一对象的同类错误累计三次即停止；已有待答问题时保留等待答复流程。补充材料、有效答复、财务说明或代码更新才建立新的纠错上下文。故障文件采用临时文件替换保存，避免半写入。

“卡住”不再触发外层自动接续；仅步数用完允许在同一次作业预算内接续。网页与回归入口共享累计 tokens 和时间预算，默认时间为1800秒，在模型调用之间检查；单个在途请求仍受模型超时和有限网络重试约束。SDK网络重试从六次降到两次，与业务修复计数分开。

DeepSeek Flash配置使用 `recovery_mode: advisor`：普通工具执行关闭思考，出错时Pro只在新的无工具会话中诊断。局部材料包最多18000字符，仅包含最近四步的相关参数、结果、参数原文和当前动作；每个问题最多咨询一次，每个纠错上下文最多六次。局部诊断使用low思考、4096输出上限、180秒请求超时；关键独立复核仍用Pro high思考。诊断只提供建议，执行和验收仍走原有绑定、独立计算与候选修复检查；诊断连接或解析失败时停止，不放行结果。

`compile_table` 首档显式字符串0可按结构起点处理，其余阈值仍须引用材料参数名称。数值误作引用时返回 `parameter.ref`、目标路径和合法写法，禁止自动猜测业务边界。参数预检失败的试算明确标为草稿，不能推进到验收阶段，下一步优先修复来源、类型和绑定。

每步记录实际服务模型、思考设置、响应/请求标识和结束原因；因长度或内容过滤未完成的输出禁止交给执行器。案卷轮次也保留最后请求信息，便于区分网络故障、输出截断和工具/业务错误。这些机制控制失败范围，不构成对未明确业务规则的自动正确性保证。最终仍须通过来源、数据关联、计算约束和独立验算。
