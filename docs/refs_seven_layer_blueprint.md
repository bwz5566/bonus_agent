# AI 财务计算系统设计蓝图（百万级数据 · 自动校准 · 可审计）

> 版本 v1.0 | 设计原则：LLM 是概率系统，财务是确定性系统。两者必须彻底解耦——**概率性认知（LLM）只做理解与编排，确定性执行（代码）垄断所有数值计算**。

---

## 0. 三条不可违反的边界

| 边界 | 含义 | 违反后果 |
|---|---|---|
| LLM 不碰数 | LLM 永不直接执行加减乘除、汇率换算、舍入 | 大数漂移、多步累积误差，无法审计 |
| LLM 不判定规则 | 规则以结构化 DSL 存储，LLM 只能"引用规则 ID"，不能解释规则 | 同一规则两次执行结果不一致 |
| LLM 不出最终结果 | 所有输出数字必须来自引擎执行产物 + 校验通过标记 | 无法建立证据链 |

任何一层违反，审计追溯即断裂。这三条边界是整套系统的"宪法"。

## 1. 总体架构：七层流水线

```
┌─────────────────────────────────────────────────────────┐
│ L7 呈现层   报告 / 差异报告 / 审计留痕包 / 血缘追溯        │
├─────────────────────────────────────────────────────────┤
│ L6 校验层   断言库 · 勾稽关系 · 对账 · 交叉复核 · 容差模型 │
├─────────────────────────────────────────────────────────┤
│ L5 执行层   确定性引擎（DuckDB/Polars）· DAG 调度 · 检查点 │
├─────────────────────────────────────────────────────────┤
│ L4 编排层   LLM Planner → 计算计划 JSON（静态校验后执行）  │
├─────────────────────────────────────────────────────────┤
│ L3 规则层   规则 DSL 库（版本化 · 生效区间 · 单元测试）    │
├─────────────────────────────────────────────────────────┤
│ L2 数据层   Bronze(原始不可变) → Silver(清洗) → Gold(汇总) │
├─────────────────────────────────────────────────────────┤
│ L1 接入层   Excel/CSV/数据库/API → 统一落 Parquet          │
└─────────────────────────────────────────────────────────┘
```

关键设计：**L1-L2 数据全程不落 LLM 上下文**。LLM 只能看到 schema、行数、列统计摘要、校验结果——明细数据以"引用 ID"形式流转。

## 2. 数值精确性工程（最容易踩坑的一层）

### 2.1 金额的内部表示：禁用浮点，二选一

| 方案 | 精度 | 性能（百万行） | 适用 |
|---|---|---|---|
| int64 最小单位（分） | 绝对精确 | 极快（原生整数运算） | **推荐**：加减乘、汇总场景 |
| decimal128（PyArrow/DuckDB） | 绝对精确 | 快（列式原生支持） | 需要多位小数中间结果（汇率、利率） |
| Decimal 对象（Python） | 绝对精确 | 慢 10-50 倍 | 仅用于最终逐笔输出校验 |
| float64 | **禁用** | — | 0.1+0.2≠0.3，百万行累积误差可达分级以上 |

int64 分单位的容量边界：±9.2 × 10^16 分 ≈ ±920 万亿元，财务场景永远够用。乘法（金额×数量、金额×税率）时用 int128 或 decimal128 防中间溢出。

### 2.2 舍入策略：必须声明式，禁止隐式

```yaml
# 规则 DSL 中的舍入声明（示例）
rounding:
  mode: ROUND_HALF_UP        # 中国财务惯例；银行家舍入=ROUND_HALF_EVEN
  precision: 2               # 舍入到分
  apply_at: output_only      # 关键：中间计算全精度，只在"输出点"舍入
```

**"output_only" 是铁律**。如果每一步中间结果都舍入到分，百万行累加后尾差可能达到几元甚至几十元；全精度计算 + 末端一次性舍入，尾差可控在 0.01 元。

### 2.3 尾差归因：必须显式规则化

价税分离、逐行舍入后汇总 vs 汇总后舍入，必然产生尾差（通常 ≤ 行数 × 0.005 元）。系统必须声明：

```yaml
tail_diff:
  tolerance: 0.01            # 单凭证容差
  attribution: largest_line  # 尾差自动摊入金额最大行
  ledger_entry: required     # 摊销动作必须记审计账
```

### 2.4 其他精度陷阱清单

- **百分比/税率**：运算顺序锁定"先乘后除" `(a * b) / c`，避免 `(a / c) * b` 的中间精度损失
- **汇率**：内部保留 8-10 位小数，换算方向（本币→外币 or 反向）必须锁定，禁止来回换算
- **单位换算**（元/万元/百万）：只在展示层换算，存储与计算永远用最小单位
- **跨期汇率重估**：每个会计期间的汇率快照落库，重算历史期间用当时汇率，不用当前汇率

## 3. 规则 DSL 设计（系统的上限由这层决定）

### 3.1 一条规则的完整结构

```yaml
rule_id: VAT_OUTPUT_GENERAL
version: "3.2.0"
name: 一般纳税人销项税额计算
effective_from: "2019-04-01"
effective_to: null
jurisdiction: CN
expression:
  output_tax: "round(amount_net * rate, 2)"
  amount_net: "amount_gross / (1 + rate)"
inputs:
  amount_gross: { type: money, unit: fen }
  rate:         { type: rate, precision: 4, allowed: [0.13, 0.09, 0.06] }
outputs:
  output_tax: { type: money, unit: fen }
tests:                          # 每条规则强制携带单元测试
  - { in: {amount_gross: 11300, rate: 0.13}, out: {output_tax: 1300} }
  - { in: {amount_gross: 10001, rate: 0.13}, out: {output_tax: 1150} }  # 尾差用例
review:
  finance_signoff: 张三 2019-03-15
  engineering_signoff: 李四 2019-03-16
```

### 3.2 规则库治理

- **双签入库**：财务专家确认业务含义 + 工程师确认实现，缺一不可
- **版本化 + 生效区间**：历史重算必须用当时生效的规则版本（as-of-date 计算），禁止用新规则重算旧账
- **LLM 与规则库的关系**：LLM 检索规则时按 `rule_id` 引用，引擎执行时按 ID 取出规则体——LLM 看到的是规则的"名片"（名称+适用范围+输入输出），不是规则本体
- **规则变更 = 代码变更**：走 PR + CI（全量跑规则测试集 + golden dataset 回归）

## 4. 计算计划（Plan）与 DAG 执行

### 4.1 LLM 的唯一产出：结构化计划

```json
{
  "plan_id": "expense_report_2026Q3",
  "steps": [
    {"id": "s1", "op": "load",   "source": "silver.journal_entries", "filter": "period='2026Q3' AND entity='CN01'"},
    {"id": "s2", "op": "apply_rule", "rule_id": "EXPENSE_CATEGORY_MAP@2.1.0", "on": "s1"},
    {"id": "s3", "op": "aggregate", "on": "s2", "group_by": ["dept", "category"], "metrics": {"amount": "sum"}},
    {"id": "s4", "op": "check",  "on": "s3", "assertion": "sum(amount) == control_total('GL', '2026Q3', 'expense')"}
  ]
}
```

### 4.2 计划静态校验（执行前必过）

1. 引用的表/字段在数据字典中存在
2. 引用的 `rule_id@version` 在规则库中存在且对该期间生效
3. 步骤间类型匹配（money 列不能直接进 qty 算子）
4. DAG 无环、无孤儿节点
5. 权限：计划不得访问未授权实体/科目

任何一条不通过 → 打回 LLM 重新生成（携带具体错误），**连续 3 次失败转人工**。

### 4.3 执行语义

- **拓扑排序执行**，每步产物落 Parquet，计算 SHA-256 哈希
- **检查点（checkpoint）**：任一步失败，从最近成功步重跑，不重复计算
- **幂等性断言**：同输入哈希 + 同规则版本 + 同计划 → 输出哈希必须一致（防止引擎非确定性 bug，如并行聚合顺序问题——浮点求和顺序敏感，整数/decimal 求和天然免疫，又一个禁用 float 的理由）
- **沙箱执行**：引擎进程无网络权限、只读数据层、写权限仅限工作区

## 5. 百万级数据的执行引擎设计

### 5.1 技术选型

| 数据规模 | 引擎 | 说明 |
|---|---|---|
| < 100 万行 | Polars / DuckDB（单机） | 列式内存计算，秒级 |
| 100万-1亿行 | DuckDB + Parquet 分区 | 单机流式，10 秒级 |
| > 1亿行 | ClickHouse / Spark | 分布式，但架构不变 |

**DuckDB 是甜点区**：直接查询 Parquet、原生 decimal128、支持谓词下推，单机即可覆盖绝大多数财务场景。

### 5.2 大数据量五条军规

1. **分区先行**：按会计期间 + 法人实体物理分区（`period=2026Q3/entity=CN01/*.parquet`），查询先剪枝，百万行先筛成几万行再算
2. **流式分块**：PyArrow RecordBatch 逐块读取，内存预算制（默认 2GB），超限自动 spill 磁盘
3. **可合并性分类**：sum/count/min/max 是代数可合并的（分块算局部值再合并）；中位数/分位数不可合并，用 t-digest 近似并标注误差界
4. **预聚合**：报表查询走 Gold 层预聚合宽表，禁止每次从明细现算
5. **控制总数分离**：总账控制数（control total）与明细计算**走两条独立路径**，在对账点汇合比对——这是"自动校准"的数据基础

### 5.3 性能预算（参考值，单机 16C/64G）

| 操作 | 100 万行 | 1000 万行 |
|---|---|---|
| 过滤+分组汇总 | < 1s | ~5s |
| 规则逐行计算（decimal128） | ~2s | ~20s |
| 双引擎交叉重算（×2） | ~4s | ~40s |
| 全链路含校验 | **< 10s** | **< 90s** |

## 6. 校验体系：五道防线（任一不过即拦截）

```
输入数据 ──▶ [①静态] ──▶ [②输入] ──▶ [③过程] ──▶ [④结果] ──▶ [⑤交叉] ──▶ 放行
              计划校验    数据质量    不变量     勾稽+对账    双引擎+抽检
```

### ① 静态校验：计划合法性（见 4.2）

### ② 输入校验：数据质量闸门
- schema 匹配、主键唯一、枚举合法、金额非负性（按科目方向）
- 空值率、异常值分布（3σ）超阈值 → 拒绝执行，输出数据质量报告

### ③ 过程断言：每步执行后的不变量
- 行数守恒：filter/join 后行数变化必须符合预期（join 不得意外扇出）
- 金额守恒：聚合前后总金额差 = 0（或 = 声明的剔除项）

### ④ 结果勾稽与对账（财务核心）
- **表内勾稽**：借贷平衡、横加=竖加、期初+本期=期末
- **表间勾稽**：现金流量表期末现金 = 资产负债表货币资金；利润表净利润 = 权益变动表本年利润
- **控制总数对账**：明细路径汇总值 vs 总账/源系统控制总数，差异 ≤ 容差 → 尾差归因记账；> 容差 → 拦截
- **容差模型**：`tolerance = max(固定值, 行数 × 0.005元)`，分级：绿（自动归因）/ 黄（标注出报告）/ 红（拦截转人工）

### ⑤ 交叉复核
- **双实现重算**：SQL 引擎与 DataFrame 引擎各算一遍，逐值比对——发现的是"引擎/实现 bug"类错误
- **历史环比**：本期结果与上期/去年同期对比，突变超阈值（如 |z| > 3）强制人工确认——发现的是"数据/业务异常"类错误
- **抽样人工**：新规则上线初期 100% 复核，稳定 90 天后降为 1% 抽检

## 7. 自动校准闭环（"自动校准计算"的实现）

校验失败不等于报错停住，而是进入校准回路：

```
校验失败
   │
   ▼
错误分类器（确定性规则，不用 LLM 猜）
   │
   ├─ 计划错误（字段不存在/规则版本错）──▶ 携带错误信息重新规划（≤3次）
   ├─ 数据错误（空值/越界/重复）──────▶ 隔离问题行 → 计算"干净子集" → 差异报告
   ├─ 尾差（≤容差）─────────────────▶ 按归因规则自动摊销 → 记审计账 → 放行
   ├─ 规则歧义（同一凭证命中多条规则）──▶ 按规则优先级裁决表 → 无优先级则转人工
   └─ 真异常（超容差差异/勾稽断裂）────▶ 拦截 + 差异报告 + 人工队列
```

**闭环学习**：人工修复的每个案例，必须回流为 (a) 一条新的规则测试用例，或 (b) 一条新的校验断言，或 (c) 规则库的修订。防止同类错误第二次走到人工。

## 8. 上下文与记忆架构（百万级数据下不遗忘的解法）

### 8.1 核心原则：数据零进上下文

LLM 上下文中永远只有四类东西：
1. 任务说明 + 当前计划
2. 数据"名片"：表名、schema、行数、列统计（空值率/极值/枚举分布）
3. 当前步执行结果摘要（成功/失败 + 关键数字）
4. 校验结果摘要

明细数据以 `dataset_id + version` 引用流转，LLM 说要算什么，引擎去取。

### 8.2 三层记忆

| 层 | 内容 | 载体 | 生命周期 |
|---|---|---|---|
| 长期 | 规则库、科目映射、口径定义 | 规则 DSL 库（RAG 检索） | 版本化永久 |
| 任务 | 计划、已完成步骤、检查点指针 | 任务状态 JSON（每轮注入） | 单次任务 |
| 产物 | 中间结果、校验记录、run manifest | Parquet + 哈希清单 | 审计保留期 |

### 8.3 长任务防遗忘

- 每轮对话固定注入"任务状态卡"：目标、计划进度（3/7 步）、最近校验结论——**不靠模型记忆，靠显式状态注入**
- 规则多时按相关性检索（向量检索 Top-K）注入规则名片，而不是全量塞入
- 超大计算拆成子任务，子任务间通过落盘产物 + manifest 接力，不依赖上下文传递

## 9. 可信度工程：上线前的三道大考

1. **Golden Dataset 对平**：取 12 期以上已审计历史报表作为基准，新系统重算，必须逐分对平（或解释每一分差异）——这是上线许可证
2. **Property-based Testing**：用 Hypothesis 随机生成百万级合成凭证，断言不变量永真（任意输入下借贷恒平衡、汇总守恒）——发现"真实数据没覆盖到"的边角
3. **混沌测试**：故意注入脏数据（空值、重复凭证、错位小数点、跨期凭证），验证拦截率 ≥ 99%，漏网案例回流为校验断言

灰度策略：**shadow run**——新系统与现有人工/旧系统并行跑 3 个月，每月对账，差异收敛到 0 后才切换主链路。

## 10. 审计与血缘

每次计算生成 **run manifest**（随产物一起归档）：

```json
{
  "run_id": "r-20261106-0042",
  "input_hashes": {"silver.journal_entries": "sha256:abc..."},
  "rule_versions": {"VAT_OUTPUT_GENERAL": "3.2.0"},
  "plan_hash": "sha256:def...",
  "steps": [{"id": "s3", "output_hash": "sha256:ghi...", "rows": 1284132, "checksum_fen": "918273645001"}],
  "checks": [{"assertion": "借贷平衡", "result": "pass"}],
  "tail_diffs": [{"amount_fen": 1, "attributed_to": "line_8842", "rule": "tail_diff.largest_line"}],
  "human_interventions": []
}
```

任意报告数字可沿 manifest 反查到：源 Parquet 文件 → 源行号 → 适用规则版本 → 计算步骤 → 校验记录。审计问询时导出整包即可。

## 11. 分阶段落地路线

| 阶段 | 周期 | 目标 | 验收标准 |
|---|---|---|---|
| P1 闭环验证 | 4-6 周 | 单一高频报表（如费用汇总）全链路跑通 | golden dataset 对平 + 校验五道防线生效 |
| P2 多表勾稽 | 6-8 周 | 三表勾稽 + 控制总数对账 + 规则库扩容 | shadow run 首月差异归因率 100% |
| P3 自动校准 | 4-6 周 | 错误分类器 + 尾差自动归因 + 人工队列 | 人工介入率 < 5% |
| P4 切换主链 | 3 个月 | shadow 差异归零后切换 | 连续 3 月零未解释差异 |

**不要跳过 P1 直接建全家系统**——规则 DSL 的格式、容差模型的参数、错误分类的边界，都要在 P1 的真实数据里磨出来。

## 12. 技术选型速查

| 组件 | 推荐 | 理由 |
|---|---|---|
| 存储格式 | Parquet（按期间/实体分区） | 列式 + 谓词下推 + 不可变 |
| 计算引擎 | DuckDB（SQL）+ Polars（DataFrame）双实现 | 单机覆盖百万-亿级；双引擎互为交叉复核 |
| 金额类型 | int64 分 / decimal128 | 精确 + 列式原生性能 |
| 校验框架 | 自研断言库（可借鉴 Great Expectations） | 财务勾稽是领域逻辑，通用框架覆盖不了 |
| 计划约束 | JSON Schema + function calling | 强制 LLM 输出合法结构 |
| 测试 | Hypothesis（property-based）+ pytest | 不变量随机测试 |
| 工作流 | 自研轻量 DAG 或 Dagster | 检查点/重放是核心需求 |
