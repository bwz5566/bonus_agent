# bonus_agent 场景化重构规划（固定规则 · 可控智能体 · 可扩展组件）

- **日期**：2026-11-06（Asia/Shanghai）
- **依据**：用户诉求（按场景固定格式/规则，禁止万能临场识别；长/短记忆、技能、MCP、长对话与结果整合）+ 三份参考材料（统一架构 v2、财务基座规范、七层蓝图）+ 现有仓 `bwz5566/bonus_agent` / 前期审查
- **原则一句话**：LLM 只理解材料与编排；**金额只来自场景绑定的确定性引擎**；新业务 = 新场景包，不往总提示词堆特例。

---

## 1. 问题与目标

### 现状痛点
1. 「能识别任何情况」→ 模型临场建模，**同一材料多次跑结果漂移、还会算错**。
2. 闸门与特例挤在巨大 `agent.py`，改一种奖金易踩另一种。
3. 缺少正式的场景选择与规则冻结；长对话无会话/工作记忆，结果难整合。

### 目标（可验收）
1. **先选场景，再算钱**：提成 / 开发 / 年度 / … 各自「固定格式 + 固定规则包」。
2. 财务后续只改**该场景的规则包与金标**，不必改通用智能体大脑。
3. 智能体路径清晰：读材料 → 对齐场景契约 → 引用规则 ID → 引擎执行 → 校验 → 发布/整合。
4. 平台能力可插：短记忆（会话）、长记忆（案卷/组织偏好）、Skill、MCP、全局工具（算表、读 Excel、析规则、读 PPT）。
5. 继续遵守：**模型不算最终金额**；无场景包不得正式结算。

### 明确不做（V1）
- 不靠一段总提示词「自适应所有奖金」。
- 不让模型心算金额或自行发明规则进正式结果。
- 不上第二套并行计算引擎；不强制微服务 / Kafka / 向量库（可后加）。

## 0. 实施约束（2026-11-06 用户确认）

- **固定格式、固定规则**：等财务后续材料到位后再写入各场景包；本阶段**不得**臆造业务规则或输入列契约内容。
- Phase A 先做：场景包**目录与 schema 骨架**、强制选场景入口、引擎/校验接线、占位 `TODO` / `status: pending_finance`；`input_contract` / `rule_package` 可为空壳或仅 schema 校验通过的占位文件。
- 财务材料到达后：只填对应 pack，不改通用 agent 大脑。
- **规则分层（产品负责人确认）**：
  1. 仓内已有规则应归纳为与场景无关的共享规则/算子库。
  2. 财务后续交付规则时，再映射/绑定到对应场景包。
  3. 冲突时以财务提交的逻辑为准（场景包覆盖通用库）。不臆造财务内容。没有可迁入实例的包保持 `pending_finance`。仓内已有季度实例的绑定方式见文末「仓内迁入」。

## 3. 场景包契约（财务「固定格式、固定规则」的落地）

每个场景目录至少包含：

```text
scenarios/packs/sales_commission/
  pack.yaml              # 元数据、契约 ID、规则绑定、数值 profile
  input_contract.yaml    # 必需表/列/粒度/期间/控制数（固定格式）
  rule_package.yaml      # 或引用已发布 rule_package_id@version
  validation_suite.yaml  # 金标、约束、对账点
  output_contract.yaml   # 明细/汇总/口径单模板
  adapters/              # 可选：列别名、单位（程序，非提示词）
  checks.py              # 可选：程序侧硬检查
  README.md              # 给人看的财务操作说明
```

**PACK 铁律**
1. 场景包**不得只含提示词**；无验证集与数值语义 → 只能探索，不能正式结算。
2. 财务给新规则：改该场景 `rule_package` + 金标用例 → PR/CI；通用 agent **不改**。
3. 场景之间规则不串用；共用算子放全局工具/引擎，业务口径放场景包。

**首批场景建议**
| pack_id | 说明 | V1 |
| --- | --- | --- |
| `sales_commission` | 提成奖金：固定表结构 + 固定提成规则 | 先做 |
| `eng_dev_bonus` | 开发奖金 | 骨架 + 规则到位后填满 |
| `annual_bonus` | 年度奖金 | 骨架 + 对齐已有 annual case |
| `custom_*` | 后续 xx 奖金 | 复制模板 |

入口：`bonus-agent auto --scenario sales_commission`；网页案卷强制选场景（取消「万能自动」为默认正式路径）。弱 triage 仅建议场景，**低置信必须人工确认**。

## 4. 智能体怎么变「清晰可控」

### 4.1 角色拆分（逻辑角色，不必立刻多进程）
1. **路由**：选定/确认场景包
2. **材料员**：用全局工具读表/PPT/PDF，产出证据与字段候选
3. **规则员**：只引用场景已绑定 `rule_id@version`（新规则只能草稿）
4. **计划员**：产出结构化计算计划（步骤 + rule_id），静态校验后执行
5. **执行器**：纯引擎，无模型
6. **校验员**：独立断言/金标；失败阻断发布
7. **报告员**：整合结果、口径单、差异说明（数字仍来自引擎）

### 4.2 一轮循环（短）
选场景 → 校验输入契约 →（缺料则 ask）→ 编译计划 → 引擎跑 → 校验套件 → 整合输出 / 待决项。

### 4.3 禁止清单（写进 CI / leakage）
- 提示词或 pack 内写死客户专名当正式规则来源（金标夹具除外且隔离）
- 模型输出金额写入正式结果
- 无场景或规则未发布就 `publish`
- 用「再跑一遍模型」代替修规则包

## 5. 全局能力 vs 场景专属

| 类型 | 能力 | 实现 |
| --- | --- | --- |
| **全局** | 读 Excel/CSV、表探测、规则草稿辅助、PPT/PDF 抽取、Decimal 计算 API、验算、差异报告 | `tools/*` + 现有 core；MCP 可外包（DB、飞书等） |
| **全局** | 短记忆（对话轮次）、长记忆（案卷摘要、已确认映射、组织偏好）、检查点恢复 | session store + workspace 持久化 |
| **全局** | Skill 注册（可复用流程说明书）、MCP 客户端 | `skills/` + `mcp/` 适配；**调用受场景白名单** |
| **场景专属** | 输入格式、规则包、校验、输出模板、额外硬检查 | 仅 `scenarios/packs/<id>/` |

Skill / MCP：**可被所有场景看见目录，但执行时按当前 pack 的 `allowed_tools` / `allowed_mcp` 过滤**，防止串场景副作用。

## 6. 记忆 · Skill · MCP · 长对话 · 结果整合

对齐蓝图「数据零进上下文」：

| 层 | 存什么 | 不进模型上下文的 |
| --- | --- | --- |
| 工作记忆（短） | 当前轮：场景 id、待决问题、计划步骤状态 | 明细行 |
| 情景记忆（中） | 本案卷：已确认映射、人工答复、校验失败点 | 全表 |
| 长期记忆（长） | 租户偏好、常用列别名、历史发布修订指针 | 原始工资明细 |
| Skill | 可复用步骤说明（如何对齐提成表） | 具体金额 |
| MCP | 外部系统读写（权限内） | 秘密明文进日志 |

**长对话**：会话 ID 持久化；打断后从检查点恢复；每轮只注入 `context_manifest`（摘要 + 引用 ID）。
**结果整合**：多步骤产物写入 `result_revision`；最终交付 = 引擎明细 + 汇总 + 证据包 + 校验通过标记；支持「多场景案卷」时分场景结果再汇总（汇总规则仍场景/规则包定义）。

## 7. 分阶段实施（可勾选）

### Phase A — 场景化止血（约 2–3 周）
- [ ] 废除「无场景正式结算」；CLI/网页强制 `--scenario` / 下拉
- [ ] 落地 pack schema + `sales_commission` **占位包**（契约/规则/金标等财务材料后填；现仅 schema + `pending_finance`）
- [ ] `eng_dev_bonus` / `annual_bonus` 注册骨架
- [ ] 拆 `agent.py` 为可测模块；场景策略只注入检查清单与工具白名单
- [ ] YAML→Decimal；清 `build/`；regress：「算错没拦住 = 0」门禁

**验收**：同材料同场景多次跑，结构化金额一致；换场景必须换规则包。

### Phase B — 可控智能体（约 2–3 周）
- [ ] 计划 JSON + 静态校验（rule_id 必须在当前 pack）
- [ ] 校验套件与发布门槛分离「试算 / 正式」
- [ ] 会话 + 案卷持久化；长任务检查点
- [ ] Skill 目录 + 1～2 个全局 Skill；MCP 适配骨架（可选先接 1 个）

**验收**：人工改规则包后金标 CI 红/绿清晰；对话中断可恢复。

### Phase C — 扩展与整合（约 3–4 周，可裁）
- [ ] 第二个完整场景（开发或年度）填满
- [ ] 结果整合：多文件交付 + 审计修订
- [ ] 更多全局工具（PPT 等）与 MCP
- [ ] （可选）生成代码沙箱路径仅探索，正式路径仍受控算子

## Phase A 骨架交付说明

已实现目录、严格占位 schema、显式场景入口及正式确认/结算阻断。详见
[场景包契约](scenario_pack_contract.md)。`eng_dev_bonus` 与 `annual_bonus` 仍为
`pending_finance / TODO`。第 0 节约束仍然优先：不把未交付的财务口径写成 `published`。

## 仓内迁入（sales_commission）

季度提成沿用仓内已有实例，不新造第四个提成包，也不把过程奖绑进本包：

- 状态是 `migrated_draft`（迁入草稿，不是财务签发，也不是 `pending_finance` 旁路字段）。
- 只绑定 `syn_acceptance` 的 QUARTER 方案、共享库里季度用到的表/变量/校验，以及数据字典和映射的子集。字段必须来自现有 `datasets.yaml`。
- 过程奖（`rules_PROCESS.yaml`、里程碑）留作以后单独的 `process_bonus`。年度实例留在 `annual_bonus`。
- 共享 DSL 仍在 `bonus_core`。以后财务映射的规则与迁入实例冲突时，以财务规则为准。
- 探索/试算不走结算闸门。正式结算要先有产品书面批准（结构化决定；设置了 `BONUS_AGENT_STATE_DIR` 时以状态库为准），再用 `bonus run --from-pack`。批准记录写明这不是财务签发，并钉住绑定指纹。
- `eng_dev_bonus` 扫过仓库：没有可迁入的开发奖金规则实例，保持纯占位。
