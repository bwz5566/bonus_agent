# 奖金核算改造方案

交付目标是财务从正式入口提交本批材料，得到可分配总额、每人应分、暂扣、待分配和舍入尾差，并能逐项说明与财务底稿的差异。材料不足时应指出受影响的对象、金额能否确定、已有依据和需要补充的具体材料。规则、人员、客户、源表和月份均随批次确定。

## 运行顺序与交接物

| 环节 | 谁执行、交付什么 | 进入下一环节的条件 |
| --- | --- | --- |
| 1. 确定输出与规则 | Flash 阅读场景、制度、补充说明及本批答复，列出应分给谁、核算期间、必需输出及其原文位置。程序登记材料指纹 | 每项输出有来源。原文确有矛盾且影响金额时，合并成一个带实例的业务问题 |
| 2. 建指标及数据关联 | 从输出倒推出每个指标的依赖、粒度、单位、期间、源表和字段、连接键、适用条件、空值与缺行、舍入位置。程序检查依赖环、键关系和原始覆盖 | 能解释一行代表什么、要算给谁、从哪取数。改名、换列和换期能重新绑定 |
| 3. 在真实对象上验证基础指标 | 程序优先执行依赖已就绪的独立分支，保留对象键、原始行、期间、分子分母、规则分支及反例；为每个指标形成可信度记录 | 已证实的冲突阻断该分支及其下游。同层其他可计算的指标继续检查。缺证据的高影响取数提交复核 |
| 4. 纠错并验证影响 | 按下文的优先级找到出错路径。模型提出有出处的最小修改，程序在副本重算原反例、受影响对象和下游 | 原反例消失，已通过的边界样例仍成立，结果的变化能从原文解释。通过后原子保存；失效的旧回执撤销 |
| 5. 计算项目并独立复核 | 确定性引擎计算项目金额和总额。独立复核从业务材料重新选择对象、来源和公式，再与生产结果逐项比较 | 项目键集合、金额、暂扣和资金去向通过。两个算法若共用同一历史来源，记录共用部分 |
| 6. 财务确认总额 | 展示当前版本、各类金额、对象范围、差异及待分项。财务确认与本版指纹绑定 | 当前版本取得真实总额确认。涉及金额或对象的修订重新核算、复核、确认 |
| 7. 计算人员、导出与验收 | 按本批角色比例、个人份额和舍入时点结算，回读实际交付的 Excel。冻结候选输出后，本地独立核对程序才打开答案底稿 | 按业务键核对项目、个人、角色原值、暂扣、待分配和尾差。逐个处置差异并登记程序、规则、材料或底稿的证据 |

## 每个指标怎样定可信度

记录绑定到方案、任务目标及当前版本。检查**规则原文、对象粒度、来源与期间、真实对象求值、独立核验**五个维度，每项给出证据状态、理由和可复查的位置。局部语法通过只能说明公式可解析。财务确认、全局守恒或整批复核只对其实际覆盖的内容有效。测到反例要保留原始对象和数值。规则草稿自报的 confidence、映射相似度和表头识别分值有各自用途，不能作为金额已核对的依据。

| 等级 | 定义 | 处理 |
| --- | --- | --- |
| CONFLICT 有反例 | 当前证据互相冲突，或程序复现了实际反例 | 优先查看冲突原件，重算对应对象；定位代码、数据或业务定义的第一处分歧 |
| UNKNOWN 未知 | 五项均缺证据 | 进入相关故障的排查队列，先取成本最低且能区分解释的证据 |
| LOW 证据不足 | 已有部分证据，前四项至少一项尚未完整验证 | 展示具体缺口；补原文、分组、期间或实际求值 |
| SUPPORTED 已获直接支持 | 前四项均已核验，独立核验待补 | 保留当前结果供复核，独立检查其适用对象和金额 |
| HIGH 已独立核验 | 五项均有当前版本的核验记录 | 后续若发现反例立即重开检查。财务确认继续按正式流程执行 |

这些是证据等级。没有对应业务频率或校准样本时，显示“85% 正确”没有可验证的含义。指标没有独立结果时，保留该维度缺口；整批复核不能普遍提升所有指标。

## 发生差异时如何回查

1. 固定失败的方案、业务键、实际值、期望行为及两方来源。先重现直接反例。若只有金额差异，沿该金额实际引用的公式、映射、原始记录向上查找。
2. 只在这条依赖链里排序。先查已证实的冲突，再查已有实际范围或期间疑点的上游，随后查其余证据较弱的依赖。并列时可看依赖距离、覆盖对象数和能否用一次本地查询消除歧义。无关分支继续，修改公式需要额外的原件或实际取值支持。
3. 举例：制度要求“各客户本年出货金额除以该客户实际出货月数”。甲一月 100 元、三月 300 元，三月底应得月均 200 元；乙仅三月出货 50 元，月均 50 元。若甲算出 300，应先查数据源实际月份；两人都返回相同的全公司值，则查分组和关联键。只有当年三月发生业务的材料完全可能正确，另一本出现更早月份仅构成核查线索。
4. 候选修复记录修改对象、依据、预计影响和可推翻该解释的样例。分别重跑原反例、同层另一对象、缺失分支及受影响金额。来源、规则或代码变更后，旧证据按指纹失效。保留已验证且依赖未变的任务。
5. 同一版本、同一失败、同一候选只验证一次。跨轮保留失败签名、试过的动作、剩余额度和断点。材料已给出唯一口径时继续计算；两种口径都会改变金额且原件无法裁决时，向财务说明两种金额及所需答复。服务故障与业务歧义分别登记。

## 实施清单与验收

执行人员从当前未通过的第一项继续。每项留下案卷、版本、已执行命令、结果、未解决反例及下一动作。任务标记通过须有对应证据。仅代码合入、模型回答“已修复”或单测数量增长都不能签发业务回执。

| 次序 | 实施工件 | 可执行的通过条件 |
| --- | --- | --- |
| A. 固定可重复的基线 | T21 冻结快照、材料清单与指纹、此前轮次与失败点 | 读同一快照得到同一批对象和公式。参考底稿隔离在验收侧 |
| B. 指标可信度与故障定位 | 任务列表与任务卡的证据等级、分组声明、异常和相关依赖排序 | 真实单值冲突优先于高分；缺证据不被当作业务错误；错误分组被指出；旧回执失效；无关低分任务不入队 |
| C. 基础指标范围检查 | 对已知类型扫描真实对象，区分确定冲突、待复核和证据缺失 | 对 T21 同一草稿指出全局库存多值、月均使用的来源月份和区域/客户汇总范围；合法全局常数、只在一个月有业务的客户通过相应正例。线索须由制度和原表裁决 |
| D. 补齐业务定义与多任务修复 | 完整指标定义、跨映射和公式的候选修改、版本化证据及受影响范围 | 新材料由模型从原文填写口径。能联动修正来源、键、粒度和公式；人为令候选最后一步失败时原工作区完整；重复同一失败新增付费调用为零 |
| E. 九月正式交付 | 从原材料生成的案卷、独立复核、财务回执、项目和人员 Excel、逐项核对 | 无人工技术代修。所有业务键、金额、待分配和尾差可解释；交换两个同额汇总下的人员金额、漏一个零金额项目或改一分钱都能被拦截 |
| F. 重复运行和跨批 | 一次连续冷启动，一次中断恢复的冷启动，一个未参与修复的独立批次 | 同批各途径逐业务键一致，跨批按自己的规则和独立依据核对。批次材料不足时登记缺项，保留已验证的层级 |

### 运行成本和持续交接

程序负责取数、全量遍历、数值计算、执行验证、排序和导出。Flash 负责从原文提出定义和修改。关键业务解释或独立核验交给已配置的 Pro；先给其必要原件，再对照程序结果。只把当前指标、相关上游和反例放入模型上下文，其他原件按坐标读取。重新运行前先看当前失败是否已有新增证据或候选，付费运行按有效授权计时计量。

每个冻结版本分别汇报首次失败环节、故障类别、人工技术干预数、已验证指标数、未解释的金额差异数、重复失败次数、用量和耗时。业务上合理的待确认单独记录。日常可用的判定采用 E 和 F 的实际交付记录。正式命令、预算、回执及精度约定见[验收计划](commission_acceptance.yaml)，执行中的待办依赖见[交付任务清单](commission_delivery_plan.yaml)。
